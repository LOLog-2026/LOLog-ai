# 실험: 컨텐츠포인트(이야기) 감지 성능 올리기

- 날짜: 2026-11-10 ~
- 담당: 민주
- 이슈: #20
- 브랜치: `feature/20-detect-eval`
- 대상 코드: `src/lolog_ai/worker/detect.py` (이야기 찾기 + 화자 나누기), LLM은 젯슨 1호 llama-server

## 목적

워커가 1시간 묶음에서 "카드로 만들 이야기"를 얼마나 맞게 찾는지 숫자로 재고, 프롬프트·온도·모델을
한 번에 하나씩 바꿔 가며 올린다. 지표는 평가 기준 문서 2절을 따른다.
지금까지 llm-bench는 속도·메모리·형식만 쟀고 정확도는 잰 적이 없다.

## 평가셋

이야기 구간이 표시된 한국어 대화 공개 데이터가 없어서 정답이 붙은 대화를 새로 썼다(실제 사람·녹음과 관계없음).
실제 친구 대화 녹음이 모이면 같은 형식(`<녹음>.json` + `<녹음>.gold.json`)으로 넣어 같은 채점기로 잰다.

| 파일 | 내용 |
|---|---|
| `evalset/stories*.json` | 이야기 100개(웃김 45, 황당 30, 추억 25). 줄마다 화자, 펀치라인 줄 번호, 종류 |
| `evalset/filler*.json` | 이야기가 아닌 대화 90묶음(약속·날씨·주문 등). 18묶음은 "ㅋㅋ", "하하"가 섞였지만 이야기는 아닌 함정(`near`) |

어려운 이야기 15개를 일부러 섞었다(`hard`): 빌드업이 긴 것 5, 다른 사람이 펀치라인을 치는 것 7, 이야기 중간에 딴말이 끼는 것 3.
이야기 100개면 재현율 0.7일 때 95% 범위가 약 ±0.09다(20개면 ±0.2). 그래서 0.1 넘는 차이는 진짜 차이로 볼 수 있다.

`make_evalset.py`가 둘을 섞어 앱이 보내는 DetectMessage 모양으로 만든다(`--seed`가 같으면 늘 같은 결과).

| 세트 | 녹음 | 정답 이야기 | 길이 | 용도 |
|---|---|---|---|---|
| `short-stt` | 25개 | 100 | 각 3~5분 | 주 지표. 짧은 입력 |
| `long-stt` | 4개 | 100 | 각 약 21분, 260구간 | 실제 1시간 묶음처럼 긴 입력. 방송 소리 25구간씩 섞임 |
| `short-clean`, `long-clean` | 위와 같음 | 100 | | 문장부호만 뺀 글. STT 오류가 얼마나 끌어내리는지 비교 |
| `nostory-stt` | 2개 | 0 | 각 10분 | 평범한 대화 오탐 |
| `tv` | 1개 | 0 | 37분 | 방송 소리 오탐 (`sample_tv_37min.json` 그대로) |

`-stt` 세트의 STT 흉내: 이어진 말 한 줄로 합치기(35%, 화자 섞임, 화제 경계는 넘지 않음), 음절 약 7%에 받침 빠짐·비슷한 모음/자음·글자 빠짐,
띄어쓰기 흔들림, 짧은 잡음 줄. 실제 SenseVoice 결과(`sample_tv_37min.json`)처럼 보이게 맞췄다.

예)
```
[5] 퇴근하고 너 피건해서 버스 타짜마자 졸았거든
[8] 또 치길래 눈 떴더니 기삭림이야 손님 종점이에요 이러시는거야 근데 던 웃긴 건 그 벙스가차고지로 들어가 있었 어
```

## 채점 (`run_eval.py`)

워커의 `detect()`를 그대로 불러 돌린다(프롬프트·`tidy`·형식 검사 모두 실서비스와 같음). `isLast=true`로 넣어 다음 묶음으로 넘기기는 끈다.

| 지표 | 재는 법 | 1차 목표 |
|---|---|---|
| F1 (P, R) | 카드와 정답 이야기 짝짓기: 구간 번호 IoU 0.3 이상이거나 정답 펀치라인 구간을 모두 품으면 맞음 | 0.6 |
| punch | 맞은 카드 중 펀치라인이 모두 안에 든 비율 | 90% |
| start / end | 맞은 카드의 시작·끝 시간 차이 중앙값(초) | 15초 |
| late | 시작이 3초 넘게 늦은(빌드업 빠짐) 비율 | |
| kind | 종류 일치 | 70% |
| spk | 한 사람만 말한 구간의 화자 정확도(화자 이름 바뀜 허용, 못 붙인 구간은 틀림) | 75% |
| fp / fp_per_h | 정답과 짝이 없는 카드 수, 1시간당 | 평범한 대화·방송 각 1개 이하 |
| fmt | JSON·길이 오류로 녹음이 통째로 실패 + 형식 검사로 버려진 카드 | 0 |
| time | 처리 시간 합(초) | 1시간 묶음 5분 |

LLM은 같은 입력에도 흔들리므로 설정마다 3번 돌려 평균(최소~최대)을 적는다. 차이가 범위 안이면 "차이 없음".
`--mock gold`(정답을 그대로 돌려주는 가짜 LLM)로 돌리면 모든 세트가 F1 1.0이 나오는 것을 확인했다.
`--skip-speakers`는 화자 나누기를 부르지 않아 시간이 크게 준다(이야기 찾기만 비교할 때). `--limit N`은 세트마다 앞 N개 녹음만 돈다.

## 젯슨 1호에서 돌리는 법

```bash
# 0) 코드 받기 (서비스용 /opt/lolog/LOLog-ai는 건드리지 않는다)
cd ~ && git clone https://github.com/LOLog-2026/LOLog-ai LOLog-ai-eval 2>/dev/null; cd ~/LOLog-ai-eval
git fetch origin && git checkout feature/20-detect-eval && git pull
cd experiments/261110-detect-eval

# 1) 평가셋 만들기 (몇 초)
python3 make_evalset.py --out sets --tv ~/llm-bench/sample_tv_37min.json
python3 run_eval.py --sets sets/short-stt --mock gold --runs 1 --tag selftest   # 모두 1이 나와야 함

# 2) 측정 중에는 감지 워커를 멈춘다(같은 LLM을 같이 쓰면 시간이 섞임). LLM 서버는 그대로 둔다
sudo systemctl stop lolog-worker@detect
export LLM_BASE_URL=http://$(sudo grep ^LLM_HOST /etc/lolog/llm.env | cut -d= -f2):8000/v1
export LLM_API_KEY=$(sudo grep ^LLM_API_KEY /etc/lolog/llm.env | cut -d= -f2)
curl -s ${LLM_BASE_URL%/v1}/health                      # {"status":"ok"}

# 3) 기준선 (tmux 안에서). 이야기 100개라 오래 걸리니 나눠서 돌린다
#   3-1 주 지표 3번 (화자 포함)
python3 run_eval.py --tag base --runs 3 --sets sets/short-stt sets/long-stt sets/nostory-stt sets/tv 2>&1 | tee results-base.log
#   3-2 STT 오류 영향 1번 (이야기 찾기만)
python3 run_eval.py --tag base-clean --runs 1 --skip-speakers --sets sets/short-clean sets/long-clean 2>&1 | tee results-base-clean.log

# 4) 끝나면 워커 다시 켜기
sudo systemctl start lolog-worker@detect
```

마지막에 나오는 표와 `results/` 폴더를 보내 주면 아래에 옮긴다.
다른 설정은 `--variant <이름> --tag <이름>`만 바꿔 같은 명령으로 돌린다(`variants.py`).
개선 실험은 먼저 `--runs 1 --skip-speakers`로 short-stt·long-stt만 돌리고, 기준선과 0.05 넘게 차이 나는 것만 3번 확인한다.

### 연구 서버(GPU)에서 돌리기

정확도는 모델 파일과 프롬프트에 달려 있으므로 같은 GGUF를 연구 서버 GPU의 llama-server에 올리면 거의 같은 값이 나온다.
프롬프트·온도 비교는 서버에서 빠르게 하고, 젯슨은 고른 설정의 시간·메모리 확인에만 쓴다.

```bash
llama-server -m Qwen3-4B-Instruct-2507-Q4_K_M.gguf --host 127.0.0.1 --port 8000 -c 24576 -np 1 -ngl 99 -fa on -ctk q8_0 -ctv q8_0 --jinja
LLM_BASE_URL=http://127.0.0.1:8000/v1 python3 run_eval.py --tag srv-base --runs 3 --sets sets/short-stt sets/long-stt sets/nostory-stt sets/tv
```
젯슨과 같은 llama.cpp 버전·같은 옵션(-c, -ctk/-ctv q8_0, -fa)을 쓴다. 기준선은 젯슨과 서버 둘 다 재서 차이를 적어 둔다.

| 설정 | long2_01 | long2_02 | 1시간 묶음 환산 | F1(2개) |
|---|---|---|---|---|

- 목표(1시간 묶음 5분)를 지금 서비스도 4배 넘는다. 개선안은 놓치던 이야기를 찾아 카드가 10 → 16~18장으로 늘고, 카드마다 부르는 화자 나누기도 늘어 더 느리다
- 젯슨은 3090보다 약 18배 느림(같은 녹음 3090 약 28초). 짧은 녹음(3.6분)의 이야기 찾기만 26초 → 출력 토큰 생성이 시간 대부분으로 보임(호출별 시간은 아직 기록 안 됨)
- 메모리: 측정 중 스왑 540 → 6,728MB(최대 7,030MB), RAM 최대 7,322MB(전부). 스왑은 거의 다 `llama-server` 프로세스(VmSwap 6.7GB, RSS 6.7GB)
- **원인: llama.cpp의 RAM 프롬프트 캐시(`--cache-ram`, b12201 기본 8,192MiB).** 지난 프롬프트 계산 결과를 호스트 메모리에 쌓는데(항목당 약 240MB, 서버 로그 `making room for prompt cache entry`),
  젯슨은 GPU와 나눠 쓰는 메모리가 7.3GB뿐이라 다 못 들어가 스왑으로 밀린다. 연구 서버 프로세스도 RSS 8.6GB. 서비스 `lolog-llm`도 같은 기본값이라 평소에도 스왑을 쓰고 있었을 것

`--cache-ram 0`으로 다시 잼(서비스 LLM을 멈추고 같은 옵션 + `--cache-ram 0`만 더해 8001번 포트로 띄움, long2_01 1개)

| 설정 | 시간(전 → `--cache-ram 0`) | 카드 | 스왑 최대 | RAM 최대 |
|---|---|---|---|---|
| base | 498초 → 687초 | 10 → 12 | 7,030MB → **193MB** | 7,322MB → **5,670MB** |
| kc8+verify-s | 839초 → 637초 | 16 → 12 | | |

- **메모리는 해결.** 서비스 설정(`lolog-llm`)에 `--cache-ram 0`을 넣어야 함(인프라 레포)
- **시간은 그대로**(카드 수에 따라 흔들림). 스왑은 주원인이 아니었다
- **진짜 원인은 출력 속도**: 입력 230~330토큰/초, 출력 **10.9토큰/초**. 화자 나누기 한 번 528토큰 = 48.6초
- 1시간 묶음 5분이려면 입력(약 90초)을 빼고 출력이 1시간에 약 2,300토큰 이하여야 한다. 지금은 약 15,000토큰으로 추정 → 6배쯤 줄여야 함
- 줄이는 방법 후보: n-gram 추측 디코딩(b12201에 `--spec-type ngram-*` 있음, 화자 나누기처럼 입력을 옮겨 쓰는 출력에 효과), JSON 공백 없애기, 화자 나누기를 줄 번호별 화자만 내게 바꾸기

#### 틀린 예에서 본 것 (`srv-base` 3번 모두, 정답 문구는 옮기지 않음)

1. **평범한 대화를 이야기로 잡음(가장 큼).** nostory 20분에 카드 17개, short의 오탐도 대부분(12.7/14)이 정답 이야기와 겹치지 않는 평범한 대화 위에 생김.
   "ㅋㅋ/하하" 함정(`near`) 근처는 오탐의 1/3뿐이고, 나머지는 식사 메뉴·준비물·일정 같은 웃음도 사건도 없는 대화. 오탐 종류는 대부분 `웃김`
2. **긴 입력에서 카드 수가 모자람.** long 녹음(정답 25개)마다 카드를 10~15개만 냄. 놓침은 입력 앞·중간·뒤에 고르게 퍼져 있어(사분위 재현율 0.43~0.54) "중간을 놓침"이 아니라 개수 자체가 적음.
   clean에서도 R 0.61로 short(0.87)보다 크게 낮음 → 긴 입력 나누기(다음 4번) 후보
3. **방송 오탐.** tv 37분에 4~5개, 매번 같은 구간(진행자 농담·영화 설명). long에 섞인 방송 조각에서는 1개/회
4. **종류 혼동.** 정답 `웃김`을 `황당`으로 가장 많이 틀림(웃김 정답 중 약 40%). 종류 정의가 겹침(웃김 "다 같이 웃을 만한 일" vs 황당 "뜻밖인 일")
5. **시작이 2줄쯤 늦음.** 맞은 카드의 약 36~42%가 정답보다 늦게 시작(중앙값 2구간). 시간 차 중앙값은 0초라 목표(15초)는 넘지만 빌드업이 잘리는 경우가 꽤 있음
6. **형식 실패 2건(3번 중).** 이야기 찾기는 정상이었고 화자 나누기 출력이 max_tokens 2048에서 잘려 녹음 하나가 통째로 실패. 반복 출력으로 보임

### C. 긴 입력 나누기 (연구 서버, 2026-11-10)

#### 무엇이 문제였나 (A-1b `srv-base-v2`의 long2 다시 보기)

- 한 번 부르면 입력 길이와 상관없이 이야기를 9개 안팎만 냄: long2 녹음당 정답 19개에 카드 8.1개. 1분당 카드가 짧은 녹음 1.04개 → 24분 녹음 0.34개
- 가운데를 놓침: 녹음 10등분 재현율 0.58 0.49 0.51 **0.21 0.29 0.15** 0.44 0.35 0.46 0.43
- 짧은 이야기가 묻힘: 짧은 이야기 재현율 0.30, 긴 이야기 0.78
- 놓친 것의 대부분은 근처에 카드가 아예 없음(358건). 경계만 틀린 것 53건, 카드 하나가 이야기 둘 이상을 묶은 것 43건
- 출력 길이(2048토큰)나 STT 오류 탓은 아님(이야기 9개 ≈ 600토큰, clean에서도 R 0.47)

#### 방법

`run_eval.py`의 `RecLlm`에서 이야기 찾기만 시간 창으로 나눠 부르고 합친다(`variants.py`의 `detect_chunk`). 줄 번호는 원래 번호 그대로 넣어
다시 맞출 필요가 없고, 겹친 곳에서 두 번 잡힌 이야기는 워커의 `tidy()`가 긴 쪽만 남긴다. 워커 코드(`detect.py`)는 아직 안 바꿈.

#### 측정 방법 고침: 요청마다 seed, 평범한 대화 세트 확대

같은 설정인데 nostory2의 오탐이 실행마다 7 / 13 / 19개로 달랐고, 같은 실행 안의 3번은 서로 비슷했다(서버가 같은 seed를 쓰는 것으로 보임).
그래서 B절까지의 3번 범위는 실제 흔들림보다 좁고, 녹음 2개짜리 nostory의 오탐 차이는 믿기 어렵다.
- `RecLlm`이 요청마다 `seed`를 새로 뽑는다
- `chat-stt`: 잡담만 녹음 8개(약 11분씩, 같은 잡담을 다른 순서로 다시 엮음)를 더했다. 이후 평범한 대화 오탐은 이것으로 잰다
- 비교를 맞추려고 base·p-kind도 같은 조건으로 다시 쟀다(`*-r3-seed`)

### D. 확인 단계 (연구 서버, 2026-11-10)

`p-kind` + 창 8분으로 찾은 후보마다(워커와 같은 `tidy()`를 거친 뒤) 그 구간만 다시 보여 주고 "4컷 카드로 다시 보고 싶을 이야기인가"를 1~5점으로 받는다
(`variants.py`의 `VERIFY_SYSTEM`, `run_eval.py`의 `RecLlm._verify`). 측정 때는 다 남기고 점수만 기록한 뒤, 몇 점 이상 남길지는 `sweep_verify.py`로 다시 계산했다.

두 방식을 1번씩 쟀다.
- `kc8+verify-s`: 점수만. 후보당 출력 17토큰, 3090에서 0.2초
- `kc8+verify`: 이유(40자)를 먼저 쓰고 점수. **llama.cpp b12201은 JSON 스키마를 JSON이 시작된 뒤부터 적용해서(lazy grammar), "이유를 먼저 쓰라"고 하면 JSON 앞에 분석 글을 후보당 약 240토큰 쓴다**(서버가 `reasoning_content`로 따로 돌려줌). 3090에서 1.4초. 지금 워커의 이야기 찾기·화자 호출은 JSON부터 바로 내서 이 문제가 없음을 확인함

빠른 측정(1번) 기준점 비교: 이유+점수는 3점 이상에서 평범한 대화 1시간당 17.7, 점수만은 4점 이상에서 9.5. 점수만이 더 빠르고 더 잘 걸러서 점수만 3번 확인했다.

### F. 확인 단계 확률 점수 (연구 서버, 2026-11-11)

### G. 화자 나누기 출력 줄이기 (연구 서버, 2026-11-11)

젯슨 시간의 75~80%가 화자 나누기라(E절) 대사를 다시 쓰지 않는 방식을 쟀다. 화자만 따로 보려고 이야기 구간은 정답을 그대로 주고(`run_eval.py --gold-detect`)
화자 나누기만 실제 모델로 돌렸다. 같은 이야기 140개(short 100, longstory 40), 3번, 요청마다 seed.

| 방식 | 출력 | short spk | longstory spk | 카드당 출력 토큰(short / longstory) | 젯슨 카드당(초, 10.9토큰/초) |
|---|---|---|---|---|---|
| base | 줄 번호 + 화자 + 대사 다시 쓰기 | **0.765 (0.761~0.774)** | **0.595 (0.588~0.604)** | 263 / 944 | 24 / 87 |
| `spk-notext` | 줄 번호 + 화자(대사 안 씀) | 0.70 (0.697~0.705) | 0.568 (0.565~0.571) | 104 / 294 | 10 / 27 |
| `spk-pairs` | `[[12,1],[13,2]]`(문법으로 공백 없이) | 0.642 | 0.548 | 29 / 87 | 3 / 8 |

- **출력을 줄일수록 화자 정확도가 떨어진다**(short 0.765 → 0.70 → 0.64). 대사를 다시 쓰는 과정이 모델이 줄을 하나씩 읽고 판단하는 데 도움이 되는 것으로 보인다. 토큰은 최대 1/10
- 구간이 정답이면 base는 short에서 목표(0.75)를 넘는다. 파이프라인 전체에서 0.64였던 것은 찾은 구간이 어긋난 영향이 크다. 긴 이야기는 구간이 맞아도 0.6
- base에서 화자 나누기 실패(출력 잘림)가 3번 중 short 2번, longstory 1번. 줄인 방식은 거의 없음(notext short 1번)
- 판정: 품질을 지키려면 대사 다시 쓰기를 유지하고 품질 영향 없는 방법(공백 없는 JSON −24%, 추측 디코딩)으로 줄이거나, 시간 목표를 위해 `spk-notext`(정확도 −0.03~0.07, 토큰 −60~70%)를 받아들일지 팀이 정해야 한다. `spk-pairs`는 손해가 커서 뺌

품질을 지키는 쪽 먼저: `spk-json`(내용은 base와 같고 JSON만 문법(GBNF)으로 공백 없이 강제), 같은 조건 3번

| 방식 | short spk | longstory spk | 카드당 출력 토큰 |
|---|---|---|---|
| base | 0.765 (0.761~0.774) | 0.595 (0.588~0.604) | 263 / 944 |
| `spk-json` | **0.806 (0.802~0.81)** | 0.578 (0.569~0.583) | **193 / 696** (−26%) |

- 토큰 26% 감소, 화자 정확도는 short에서 오르고(+0.04) longstory에서 조금 내림(−0.02). 품질 손해 없이 쓸 수 있는 것으로 본다
- 다음: 추측 디코딩이 젯슨에서 실제 몇 배인지 `jetson_spec_bench.sh`로 잰다(plain / n-gram / 작은 draft 모델)
